# quadruped_train 训练调参教程

[文档导航](README.md) | [TensorBoard 指南](TensorBoard使用指南.md)

参数以训练仓库对应机器人的配置及通用基类为准。Go2与Primuus独立继承base，不互相读取配置；文中明确标为Go2的数值不能直接覆盖Primuus。调节范围用于说明实验方法，不是最佳参数，也不代表历史checkpoint采用了这些配置。

## 阅读顺序

1. 先看“任务与配置边界”和“参数如何生效”，区分正式功能与预留字段。
2. 按“reward 参数”“command 参数”“控制参数”选择一个参数组。
3. 需要增加新功能时再看“新增 reward 或域随机化”，不要重复添加已有项。
4. 运行前确认“续训还是从头训练”和“哪些改动需要同步部署侧”。

这份文档用于记录当前 `quadruped_train` 的调参方法。重点说明正式参数如何生效、哪些数值会明显影响训练、哪些改动可以续训、哪些改动需要从头训练，以及哪些训练侧改动需要同步到本地部署侧 `quadruped`。

```text

estimator: 历史270 -> 速度3 + latent16
actor input: 当前45 + 速度3 + latent16 = 64
critic privileged obs: 45 + base_lin_vel3 + external_force3 + height_scan187 = 238
policy: HIMActorCritic
algorithm: HIMPPO
runner: HIMOnPolicyRunner
```

| --- | --- | --- |
| `base_height` | `-0.4` | 站立、移动和转向共用高度容差 |
| `collision` | `-1.0` | 持续大腿/小腿非足端接触惩罚 |

| 控制项 | Go2训练 | Primuus训练 | Primuus MuJoCo |
| --- | --- | --- | --- |
| 物理步长 | 5 ms | 2 ms | 0.5 ms |
| decimation | 4 | 10 | 40 |
| 策略周期 | 20 ms | 20 ms | 20 ms |
| PD周期 | 每物理步 | 每物理步 | 每物理步 |
| PD增益 | `20 / 0.5` | `60 / 1.5` | `60 / 1.5` |
| 动作缩放 | `0.25` | `0.25` | `0.25` |
| 关节损耗 | 原生引擎参数 | Jenkins统一模型 | Jenkins统一模型 |

Go2的MuJoCo配置另用2 ms、decimation=10，同样是50 Hz策略周期。Primuus默认每腿角度为 `[0, -0.75, -1.5]`，不能复制Go2的大腿正角度。

**预留字段不是已完成功能：** 当前 `create_sim()` 只创建平地，`terrain.py` 未接入主链路；critic 的外力3维、高度187维仍为零占位。电机强度、PD 随机化、控制延迟也尚无正式实现，不能只添加一个范围就认为已启用。

## 参数如何生效

每项训练功能保留一个正式配置来源，不添加与实际参数重复的启用gate。实机 `RealSafetyManager`、最终输出安全门、FAULT和watchdog是独立安全边界，不能通过修改reward权重关闭。

| 功能 | 配置来源或当前状态 |
| --- | --- |
| reward | `rewards.scales.<name>`，非零启用，零关闭 |
| 观测噪声 | `noise.add_noise` |
| 地面/形状接触摩擦随机化 | `domain_rand.randomize_friction`，不是关节损耗随机化 |
| Primuus关节损耗 | `asset.joint_dynamics_file`及其引用的JSON，Go2不启用 |
| 质量随机化 | `domain_rand.randomize_base_mass` |
| 随机外推 | `domain_rand.push_robots` |
| 速度命令课程 | `commands.curriculum` |
| 地形课程 | `terrain.curriculum` 为预留字段，当前链路未接入 |
| 高度采样 | `terrain.measure_heights` 为预留字段，当前没有真实高度回填 |

45×6 历史观测、`HIMActorCritic`、`HIMPPO` 和 `HIMOnPolicyRunner` 是当前框架结构，不再通过额外布尔量启用。`foot_clearance` 权重非零时，环境会自动获取并刷新它需要的 rigid-body state。

参数覆盖顺序是：通用基类默认值 -> 机器人实例覆盖 -> CLI 支持的覆盖项。本文中省略外壳的 Python 代码只是字段片段；实际修改机器人配置时，应保持现有嵌套类继承，例如 `class rewards(LeggedRobotCfg.rewards)` 和 `class scales(LeggedRobotCfg.rewards.scales)`，不要用一个全新的同名类遮蔽其他继承参数。

`feet_stumble`配置对应的实现名是 `_reward_stumble`，而自动发现要求 `_reward_feet_stumble`；该项保持零权重。若需要启用，必须先使名称与实现对应，不能直接把权重改为负值。

### Primuus关节损耗与接触摩擦

`joint_dynamics.json`统一两引擎的非零关节损耗：干摩擦屈服力矩0.05 N m、粘性阻尼0.02 N m s/rad、预滑移刚度5 N m/rad。它们是待实物标定的仿真假设，不是PhysX摩擦系数到MuJoCo力矩的数值换算。

训练适配器运行时替换原生DOF friction/damping，每个物理步根据实际位移计算被动损耗；MuJoCo通过YAML的 `simulation_joint_dynamics_path`显式选择相同定义。电机PD、限矩和奖励中的 `torques`仍只表示电机输出，被动损耗另行施加。复位清除摩擦历史，不通过清零速度制造静摩擦。

`domain_rand.friction_range`改变的是形状接触摩擦，不会随机化上述关节参数。足地摩擦仍由各引擎接触模型求解；同一关节损耗公式不保证接触轨迹完全一致。原理、力矩通道和裸Viewer区别见[关节动力学](关节动力学.md)。

## 新增 reward 或域随机化

这一节说明的不是“把已有参数从 `0.0` 改成非零”，而是给框架增加一个以前不存在的 reward 或随机化项时，代码应该放在哪里、哪些地方必须同步修改。

先区分两类需求：

```text
已有 reward / 随机化项，只是启用或调权重：通常只改对应机器人配置。
以前不存在的新项：需要配置 + 实现；实现放在通用层或机器人适配层，并显式声明额外状态依赖。
```

训练侧的分层约定如下。以后新增其他四足机器人时，通用逻辑保持在 `base`，机器人差异放在对应机器人目录，避免把 Go2 专有逻辑写进框架核心。

| 位置 | 负责内容 | 新增时是否通常需要改 |
| --- | --- | --- |
| `quadruped_rl/envs/base/legged_robot_config.py` | 所有四足机器人的默认配置、默认关闭的开关和注释 | 是，新增通用配置字段时 |
| `quadruped_rl/envs/go2/go2_config.py` | Go2 的实际权重、范围和开关 | 是，给 Go2 启用或覆盖参数时 |
| `quadruped_rl/envs/primuus/primuus_config.py` | Primuus独立权重、范围和开关 | 是，给Primuus启用或覆盖参数时 |
| `quadruped_rl/envs/base/legged_robot.py` | reward 计算、状态 buffer、reset 和物理步主流程 | 新 reward 或动态随机化时 |
| `quadruped_rl/envs/go2/go2_env.py` | Go2 任务适配器，可覆盖 Go2 专有行为 | 仅公式或行为确实只适用于 Go2 时 |
| `quadruped_rl/envs/base/rewards.py` | reward 所需额外状态的集中声明 | 新 reward 依赖额外状态 tensor 时 |
| `quadruped_rl/envs/base/domain_rand.py` | 资产属性随机化和 push | 新增域随机化实现时 |
| `quadruped/src/controller/rl/...` | 本地 MuJoCo 推理 | 仅 reward/随机化通常不用改 |

### 先确认是不是已有项

先在训练仓库查找同名函数和配置：

```bash
cd ~/quadruped_train
rg -n "base_height|foot_clearance" quadruped_rl/envs
```

例如当前已有 `_reward_base_height()`，且 Go2 已使用 `-0.4`。若只是增强它，不要再写函数，可以在保留其他参数的前提下覆盖权重；下面的 `-0.5` 是调整示例，不是当前默认值：

```python
# quadruped_rl/envs/go2/go2_config.py
class rewards(LeggedRobotCfg.rewards):
    class scales(LeggedRobotCfg.rewards.scales):
        base_height = -0.5  # 高度误差是代价，因此使用负权重
```

这种改动不改变 actor、critic、观测或动作维度。可以用 checkpoint 续训，但因为优化目标变了，短期曲线下降是正常现象。

### 新增一个 reward 的完整步骤

以下以已经实现的 `foot_slip` 回顾完整接入路径。当前 Go2 已启用 `-0.10`，不要照抄后再新增一个同名实现。新增真正的新项时，按相同流程使用唯一名称；示例中的起始权重只演示试验方法，不替换当前配置。

#### 1. 先定义名称和数值方向

名称必须在配置和函数名中完全一致：

```text
配置 key:       foot_slip
环境函数:       _reward_foot_slip(self)
TensorBoard:    Episode/rew_foot_slip
```

当前框架会自动寻找每一个非零 scale 对应的 `_reward_<名称>` 函数；不需要手动把它注册到 `compute_reward()`。

权重的正负由函数返回值的含义决定：

```text
函数返回“越大越好”的量，例如成功率、速度跟踪得分：正权重。
函数返回误差、能耗、碰撞次数等“越小越好”的代价：负权重。
```

不能仅按名称或某次函数返回值的正负决定权重。例如 `feet_air_time` 在落地时返回 `air_time-0.5`，可以为正也可以为负；正权重表示更长腾空更有利，不代表每一步都产生正奖励。先读函数定义和期望方向。

`foot_slip` 返回的是速度平方代价，所以应从负权重开始。不要为了使用正权重而在函数里额外取负；统一由 scale 表达奖励或惩罚，调参更容易比较。

#### 2. 在配置中声明，但默认关闭

如果该 reward 对所有四足机器人都有相同语义，先在 `quadruped_rl/envs/base/legged_robot_config.py` 的 `rewards.scales` 中加入字段，并写中文注释：

```python
class scales:
    # ...已有项...
    foot_slip = -0.0  # 足端接触时的水平滑动惩罚，默认关闭
```

默认使用 `-0.0`，原因是 `_prepare_reward_function()` 会移除 scale 为零的项。这样所有尚未验证的机器人默认不会因为缺少实现或数据依赖而启用该项。

若公式只对 Go2 成立，例如依赖 Go2 特有的 body 名称、关节结构或机构参数，则可以只在 `go2_config.py` 的 `rewards.scales` 中声明，并保持其他机器人配置没有该字段。不要把这种特例放进通用默认配置。

#### 3. 在具体机器人配置中给出初始权重

在 `quadruped_rl/envs/go2/go2_config.py` 中覆盖，而不是直接修改 Go2 以外机器人也会继承的默认值：

```python
class rewards(LeggedRobotCfg.rewards):
    class scales(LeggedRobotCfg.rewards.scales):
        foot_slip = -0.02  # 起始值；先用小权重验证，不要一次压制步态探索
```

新 reward 的首轮权重应明显小于速度跟踪主项。先让 TensorBoard 显示它的量级，再决定是否增强；不要只凭不同 reward 的原始数字直接比较，因为每项单位和公式不同，且框架会把非零 scale 乘以控制周期 `dt`。

#### 4. 在正确的环境层实现向量化函数

对所有四足都成立的公式，放在 `quadruped_rl/envs/base/legged_robot.py` 的 reward 区域。只适用于 Go2 的公式，则放进 `quadruped_rl/envs/go2/go2_env.py`，由 `Go2Env` 覆盖或新增同名方法。`Go2Env` 继承 `LeggedRobot`，所以自动发现机制会查找到两种位置的函数。

无论放在哪里，函数都必须返回形状为 `(num_envs,)`、位于 `self.device` 上的 tensor；不要为 4096 个环境写 Python 循环。下面以通用层的实现为例：

```python
def _reward_foot_slip(self):
    # 接触足端的水平速度平方和；返回值越大表示滑动越明显。
    foot_contact = self.contact_forces[:, self.feet_indices, 2] > 1.0
    foot_speed_sq = torch.sum(torch.square(self.feet_vel[:, :, :2]), dim=-1)
    return torch.sum(foot_contact * foot_speed_sq, dim=1)
```

当前 reward 执行链路是：

```text
Go2 rewards.scales.foot_slip 非零
        -> LeggedRobot._prepare_reward_function() 自动找到 _reward_foot_slip
        -> 每个控制步由 compute_reward() 调用并累计到 episode_sums
        -> 回合结束时自动写入 Episode/rew_foot_slip
```

因此，除 `termination` 这个特殊项外，不需要改 `compute_reward()`、`episode_sums` 或 TensorBoard logger。

#### 5. 处理额外状态依赖

`foot_slip` 用到 `self.feet_vel`，它来自 Isaac Gym 的 rigid-body state。此类 reward 需要在集中依赖集合中声明：

```python
# quadruped_rl/envs/base/rewards.py
QUADRUPED_RIGID_BODY_STATE_REWARDS = frozenset({
    "foot_clearance",
    "foot_slip",
    "turn_step",
})
```

环境会检查这些 reward 的权重：只要其中任意一项非零，就自动获取并刷新 rigid-body state。权重全部为零时不会承担这部分状态刷新开销。

若新 reward 只使用已有的 `dof_pos`、`dof_vel`、`actions`、`base_ang_vel`、`projected_gravity` 或 `contact_forces`，不需要修改 `base/rewards.py`。reward 本身的非零 scale 就是启用开关，不再增加第二套布尔 gate。

如果某项计算成本很高，仍然应使用 `rewards.scales.<name> = 0.0` 关闭；`_prepare_reward_function()` 会直接移除对应函数，不会在每个控制步调用它。

#### 6. 新 reward 的最小验证流程

```bash
cd ~/quadruped_train
python quadruped_rl/scripts/train_go2.py --headless --max_iterations 5
```

先确认没有以下问题，再做长训：

- 启动阶段出现 `AttributeError: _reward_xxx`：scale 名称与函数名不一致，或漏写函数。
- reward shape 报错：函数没有对足端、关节等维度做 `sum(..., dim=1)`，返回了 `(num_envs, num_feet)` 等二维结果。
- CUDA 相关报错：检查 tensor 是否在 `self.device`、是否混用了 CPU tensor，以及是否存在 Python 标量/布尔判断作用于 GPU tensor。
- TensorBoard 没有 `Episode/rew_xxx`：检查 scale 是否非零，并等待至少一个 episode 结束。
- 总 reward 上升但机器人变差：单独查看新项、速度跟踪、episode length 和 play 画面，不能只看 `Train/mean_reward`。

### 新增一个域随机化的完整步骤

摩擦、质量和 push 等训练随机化本身不新增 actor 输入，也不要求部署时复现同一组随机数。部署仍要满足观测/动作与标称物理参数契约。如果新增的随机化改变控制周期、关节映射或动作语义，就必须重新核对部署，不能一概理解成“随机化都不用同步”。

先判断随机化在哪个时机生效：

| 类型 | 典型项 | 当前框架放置位置 | 生效频率 |
| --- | --- | --- | --- |
| 资产创建时的静态属性 | 地面摩擦、机身质量、碰撞形状属性 | `base/domain_rand.py` 的 property callback | 每个并行环境创建一次 |
| 回合重置时的状态 | 初始姿态、初始速度、命令、可重置的环境参数 | `base/legged_robot.py` 的 `reset_idx()`、`_reset_*()` | 每个 episode |
| 运行中的动态扰动 | push、外力、移动平台 | `post_physics_step()` 或其回调 | 按配置周期 |

不要把“每回合都要重采样”的逻辑写进资产创建 callback。环境在训练启动时只创建一次，写错位置会导致随机化只采样一次，和预期的每回合随机化不同。

#### 示例：新增静态的接触恢复系数随机化

以下以 `restitution` 为例，展示新增一个与摩擦同类的随机化项需要改哪些地方。

1. 在 `base/legged_robot_config.py` 的 `domain_rand` 声明默认关闭的字段：

```python
class domain_rand:
    # ...已有项...
    randomize_restitution = False  # 是否随机化碰撞恢复系数
    restitution_range = [0.0, 0.1]  # 恢复系数随机范围
```

2. 在 `go2/go2_config.py` 的 `domain_rand` 覆盖实际开关和范围：

```python
class domain_rand(LeggedRobotCfg.domain_rand):
    randomize_restitution = True  # 示例新功能：为Go2启用恢复系数随机化
    restitution_range = [0.0, 0.05]  # 示例取值，不是当前已有参数
```

3. 在 `process_quadruped_rigid_shape_props()` 中直接读取 `randomize_restitution`，采样并写入 Isaac Gym 的刚体形状属性。应沿用现有摩擦随机化的“每个环境一个 bucket”模式，避免每个 shape 都独立随机而引入不必要的物理不一致：

```python
if env.cfg.domain_rand.randomize_restitution:
    if env_id == 0:
        low, high = env.cfg.domain_rand.restitution_range
        num_buckets = 64
        bucket_ids = torch.randint(0, num_buckets, (env.num_envs, 1))
        buckets = torch_rand_float(low, high, (num_buckets, 1), device="cpu")
        env.restitution_coeffs = buckets[bucket_ids]

    for shape_id in range(len(props)):
        props[shape_id].restitution = env.restitution_coeffs[env_id]
```

这个例子只展示接入结构。恢复系数会明显改变触地行为，Go2 平地 walk 不应一开始就打开大范围随机化；先从接近 `0.0` 的窄范围开始，确认不会破坏接触稳定性。

#### 回合级或动态随机化的额外要求

若新项不是资产静态属性，除了配置外还要选择正确的执行点：

- 每回合重置：在 `_reset_dofs()`、`_reset_root_states()` 或 `reset_idx()` 中只更新 `env_ids` 对应的环境，并在需要时调用 Isaac Gym 的 indexed setter 把结果写回仿真。
- 每控制步扰动：使用 GPU tensor 进行批量采样，避免在 4096 个环境上写 Python 循环；随后通过对应的 Isaac Gym tensor API 提交状态或力。
- 改变 PD、关节强度等控制参数：需要明确参数是每环境还是全局。当前 `p_gains` / `d_gains` 是每关节的一维共享值；若要按环境随机，必须先把它们扩展为 `(num_envs, num_actions)` buffer，并同步修改 `_compute_torques()`，不能只在配置里加一个范围。
- 新增外力并希望让 HIM critic 利用该信息：可以考虑更新现有 privileged external-force 槽位；不要随意改 actor 的 45 维单帧观测或 6 帧历史长度。改 actor/critic 维度会使 checkpoint 不兼容，并要求同步部署侧输入构造。

### 新增项的检查表

新增 reward：

- 在 `base` 配置声明默认字段并写中文注释。
- 通用项在 `base` 实现并在对应机器人配置给出启用值；机器人专有项放进对应适配器，避免污染通用层。
- 名称严格满足 `scales.<name>` 对应 `_reward_<name>()`。
- 函数返回 `(num_envs,)` 的 GPU tensor，使用批量运算。
- 有额外状态依赖时，在 `base/rewards.py` 声明，并确认对应 state tensor 已获取和刷新。
- 使用 reward scale 作为唯一启用开关，不再增加重复布尔 gate。
- 做 5 次迭代冒烟测试，并在 TensorBoard 确认 `Episode/rew_<name>`。

新增域随机化：

- 在 `base.domain_rand` 声明开关和范围，在机器人配置覆盖实际值。
- 实现逻辑直接读取对应 `domain_rand` 开关。
- 静态属性写进 rigid shape/body property callback；回合级和动态项写进 reset 或 post-step 流程。
- 只影响目标 `env_ids`，并使用相应 Isaac Gym setter 写回仿真。
- 随机范围从小开始；每次只增加一种随机化，先验证 reward、episode length 和 play。
- 不改变观测/动作/控制接口时可尝试 `--resume`；若改变 actor 或 critic 输入维度、动作维度或网络结构，则必须从头训练。

以下已经实现且不改变接口的训练侧改动通常不需要同步部署侧；尚未实现的功能必须先接入代码：

```text
reward 公式和权重
摩擦、质量、恢复系数等训练域随机化
push、课程学习、训练噪声
PPO / HIM-PPO 超参数
```

以下改动必须同步部署侧，并重新核对导出的 TorchScript / ONNX 输入：

```text
actor 观测内容、顺序、缩放、历史帧数
动作维度、关节顺序、默认关节角
action_scale、kp、kd、控制周期
```

## 常见功能怎么打开

### 1. 打开 foot_clearance

用于鼓励足端离地，避免策略拖脚。当前已经打开。

只需要设置目标高度和非零权重：

```python
class rewards:
    clearance_height_target = -0.20

    class scales:
        foot_clearance = -0.01
```

注意：

- `foot_clearance` 依赖足端刚体位置和速度，框架会根据非零权重自动刷新 rigid-body state。
- 将 `foot_clearance` 设为 `0.0` 或 `-0.0` 就会关闭该项。
- 当前 `clearance_height_target = -0.20` 是机身坐标系下的足端目标高度，不是世界坐标直接抬 20 cm。
- 当前只计算非支撑足；高度误差先除以 `clearance_height_sigma=0.05 m` 再平方，并乘以机身系水平相对摆动速度。相对速度扣除了机身平移和旋转。
- 这不是“保证抬脚”的硬约束：不摆腿也可能获得很小的惩罚，必须同时观察换步、滑移和非足端支撑。

可调范围建议：

```text
foot_clearance = -0.005  # 很弱
foot_clearance = -0.01   # 常用起点
foot_clearance = -0.02   # 更强，可能导致动作变大或步态过高
```

### 2. 打开观测噪声

用于增强鲁棒性，当前已经打开。

```python
class noise:
    add_noise = True
    noise_level = 1.0
```

各项噪声：

```python
dof_pos = 0.01
dof_vel = 1.5
lin_vel = 0.1
ang_vel = 0.2
gravity = 0.05
height_measurements = 0.1
```

当前45维 actor 只对角速度、重力投影、关节位置和关节速度加噪；命令和上次动作不加噪。`lin_vel`、`height_measurements` 噪声字段不会自动给当前 actor 增加对应观测。每一新帧采样一次噪声后进入历史，旧帧不反复重新加噪。

建议：

- 初期如果训练明显发散，可以先把 `noise_level` 降到 `0.5`。
- 不建议一开始把噪声放大到 `2.0` 以上。
- 噪声不会改变模型输入维度，可以在 checkpoint 上续训。

### 3. 打开摩擦随机化

当前已经打开：

建议范围：

```text
[0.3, 1.5]    # 更激进，建议步态稳定后再试
```

### 4. 打开机身质量随机化

当前关闭。

```python

    randomize_base_mass = True
    added_mass_range = [-1.0, 1.0]
```

建议先从小范围开始：

质量随机化不会改变 obs/action 维度，通常可以续训，但会让短期 reward 下降。

### 5. 打开 push

当前关闭。push 会周期性给机器人一个平面速度扰动。

```python
class domain_rand:
    push_robots = True
    push_interval_s = 15
    max_push_vel_xy = 1.0
```

建议顺序：

```text

```

### 6. 打开 command curriculum

当前关闭。用于根据速度跟踪表现逐步扩大命令范围。

```python
class commands:
    curriculum = True
    max_curriculum = 2.0
```

注意：

- 这会改变命令采样范围，训练曲线可能短期下降。
- 适合基础速度跟踪稳定之后打开。
- 当前课程只扩展前向命令范围，不自动扩大横移或偏航；`max_translation_speed` 仍限制最终XY模长。只把 `max_curriculum` 改为2.0而保留合成上限1.0，不会训练到2 m/s。

### 7. 地形和高度采样的实际边界

当前关闭：

```python
terrain.mesh_type = 'plane'
terrain.curriculum = False
terrain.measure_heights = False
```

这些字段目前不能作为粗糙地形功能开关使用。`LeggedRobot.create_sim()` 无条件创建 ground plane，没有 heightfield/trimesh 创建分支和地形课程更新；`privileged_height_scan_obs` 仅初始化为零，尚无实际高度回填。

要支持真实粗糙地形，需要先实现并检查：地形生成与创建、机器人起点、地形高度查询、reset/课程推进、187维高度数据及缩放。保持 actor 为270维与接入真实 critic 高度是两个不同问题。当前不要仅设置三个布尔量就启动“粗糙地形训练”。

## reward 参数怎么理解

当前 Go2 生效的主要 reward：

```python
tracking_lin_vel = 1.0
tracking_ang_vel = 0.5
lin_vel_z = -2.0
ang_vel_xy = -0.05
orientation = -0.2
dof_acc = -2.5e-7
foot_clearance = -0.01
action_rate = -0.01
smoothness = -0.01
torques = -0.0002
dof_pos_limits = -10.0
base_height = -0.4
collision = -1.0
foot_slip = -0.10
turn_step = 0.1
stand_still = -0.1
stand_contacts = -0.4
```

reward 权重会在环境初始化时乘以控制周期 `dt`。当前：

```text
sim.dt = 0.005
control.decimation = 4
训练控制周期 dt = 0.02
```

所以不要只看原始数字大小，还要知道实际计算时会乘 `0.02`。

### tracking_lin_vel

鼓励跟踪 x/y 速度命令。

```python
tracking_lin_vel = 1.0
tracking_sigma = 0.25
```

影响：

- 增大后更重视速度跟踪。
- 太大可能牺牲姿态稳定和动作平滑。
- 如果实际速度总是偏离命令，可以优先看这个和命令范围。

### tracking_ang_vel

鼓励跟踪 yaw 角速度。

```python
tracking_ang_vel = 0.5
```

影响：

- 增大后转向更积极。
- 太大可能导致转向时身体晃动。

### lin_vel_z

惩罚机身上下跳动。

```python
lin_vel_z = -2.0
```

影响：

- 过弱会跳动。
- 过强可能让步态不敢抬腿。

### orientation

惩罚机身 roll/pitch 倾斜。

```python
orientation = -0.2
```

影响：

- 增大负值后机身更平。
- 过强可能抑制自然动态步态。

### torques

惩罚力矩。

```python
torques = -0.0002
```

影响：

- 更负会省力，但可能脚抬不起来、速度上不去。
- 更接近 0 会动作更有力，但可能抖动和能耗变大。

建议调节：

```text
-0.0001   # 更允许用力
-0.0002   # 当前值
-0.0004   # 更省力但可能拖脚
```

### action_rate

惩罚相邻动作变化。

```python
action_rate = -0.01
```

影响：

- 更负会动作更平滑。
- 太强会让动作迟钝，脚抬不起来。

### smoothness

惩罚二阶动作变化。

```python
smoothness = -0.01
```

影响：

- 抑制高频抖动。
- 太强会限制快速摆腿。

建议：

```text
-0.005
-0.01
-0.02
```

### foot_clearance

鼓励足端在摆动时达到目标高度。

```python
foot_clearance = -0.01
clearance_height_target = -0.20
```

影响：

- 有助于解决不抬腿和拖脚。
- 太强可能导致步态夸张、能耗增加、落脚不稳。

建议优先调 `foot_clearance` 权重，再调 `clearance_height_target`。

### dof_pos_limits

惩罚关节接近位置极限。

```python
dof_pos_limits = -10.0
soft_dof_pos_limit = 0.9
```

影响：

- 减少关节打到极限。
- 太强可能压制动作幅度。

这是 Unitree Go2 配置里启用的项，当前已经打开。

### collision

当前已经启用：

```python
collision = -1.0
collision_force_threshold = 5.0  # 非足端接触力阈值 [N]
collision_min_contact_time = 0.06  # 持续接触时间阈值 [s]
```

大腿/小腿超过力阈值且持续接触时计罚，不直接终止回合；Go2 的机身接触和姿态越界由终止逻辑处理。`Episode/contact_<body>` 记录接触时间占比，不能与 reward 数值等同。

减弱或增强的试验值：

```text
collision = -0.2
collision = -0.5
collision = -1.0
```

这是软优化目标，不能代替仿真碰撞体。Go2 当前 `asset.self_collisions=1` 会关闭机器人内部自碰撞，不会关闭地面接触；非足端触地惩罚与模型自碰撞过滤是两件事。

### base_height、stand_still、stand_contacts

Go2 站立、平移和转向共用 `base_height_target=0.28 m`、`base_height_tolerance=0.03 m`，在0.25-0.31 m内不惩罚，允许步态上下浮动：

```text
excess = max(abs(base_z - 0.28) - 0.03, 0)
height_cost = (excess / 0.05)^2
```

当前高度使用平地世界坐标的机身根节点 z；`init_state.pos.z=0.42 m` 是初始落地位置，不是行走高度目标。高度奖励本身不会触发 reset。

站立专用项要求 `norm(command_xy)<=0.1 m/s` 且 `abs(command_yaw)<=0.1 rad/s`。`stand_still=-0.1` 惩罚偏离默认角；`stand_contacts=-0.4` 惩罚未支撑足比例，支撑力阈值5 N并允许一帧漏检。`stand_height=0` 避免与全局高度重复。原地转向不应被当成站立。

### foot_slip、turn_step

`foot_slip=-0.10` 惩罚接触足端世界系水平速度平方和。提高负权重可以抑制滑步，但过强也会压制调整落脚位置的能力。

`turn_step=0.1` 要求腾空0.08-0.45 s、相对上次接触高度至少抬升0.035 m，并满足偏航命令阈值0.12 rad/s。每足最多积累0.5 s奖励预算，奖励还乘以XY/yaw跟踪分数和同向转动进度，持续非足端支撑时关闭。不是“落地次数越多就越好”，不能用提高频率刷分。

先看 `Command/turn/*` 和 `Command/moving_turn/*`，再决定调换步门槛、滑移代价还是转向采样比例；不要只加大角速度跟踪权重。

### feet_air_time

当前关闭：

```python
feet_air_time = 0.0
```

传统 legged_gym 常用 `1.0`，但 HIMLoco walk 配置里经常关闭或给得很小。

影响：

- 打开后可能更容易产生明显步态。
- 太大可能鼓励跳跃或过长腾空。

建议：

```text
feet_air_time = 0.1
feet_air_time = 0.2
feet_air_time = 0.5
```

不要一开始直接用 `1.0`，除非当前策略很稳但步态太保守。

## 控制参数怎么调

影响机器人跟踪目标关节角的力度。

```text
kp 太小：腿软，脚可能抬不起来

```

动作到目标关节角偏移的比例。

```python
target_joint_pos = default_joint_angle + action * action_scale
```

- 太小：动作幅度不足，脚抬不起来。
- 太大：动作激进，容易抖动或摔倒。

当前：



## 续训还是从头训练

适合 `--resume`：

- 只微调 reward 权重。
- 打开小范围噪声。
- 打开小范围摩擦随机化。
- 打开轻量 push。
- 调整 command 范围但不改 obs/action 维度。
- 调整 PPO 学习率、entropy 等。

不建议 `--resume`：

- 改了 actor obs 维度。
- 改了 history length。
- 改了 privileged obs 维度。
- 改了 action 维度。
- 改了网络结构。
- 改了关节顺序。
- 大改默认关节角、PD、action_scale。
- 从平地突然切到复杂地形且随机化全开。

在保持 `45*6`、HIM-PPO及机械/控制契约不变时，小幅调整reward、noise、接触摩擦随机范围或push通常可以续训。改变Primuus关节损耗公式、参数或接入方式属于动力学变化，不等同于扩大地面摩擦随机范围；应先建立独立训练基线，再决定是否以旧权重微调。

“可以加载”不等于“续训一定合适”。换机器人、关节顺序、物理模型或优化目标大改，即使维度相同也不应直接复用策略。`--max_iterations` 在 resume 时是本次追加迭代量：从1000恢复再跑500，目标编号约1500。

## 推荐调参顺序

每次只改一个参数组，不要一次性全开。

默认配置中生效的项：

```text
HIM-PPO + 45*6
smoothness
foot_clearance
noise
friction randomization
dof_pos_limits
base_height / collision
foot_slip / turn_step
stand_still / stand_contacts
```

排查与调节顺序：

```text
1. 先核对模型接触、关节顺序、默认姿态、动作/观测缩放和策略频率
2. 用零命令检查站立高度与四足支撑，再分别检查平移、原地转向、边走边转
3. 按现象微调已开启的高度、碰撞、滑移、抬脚和转向换步奖励
4. 再调 smoothness、action_rate、torques，避免过度惩罚压制摆腿
5. 基础步态稳定后单独增加 push、质量随机化或扩大已有随机范围
6. 新地形、真实高度输入、电机随机化和延迟需先实现，不是当前可直接打开的功能
```

如果机器人仍然脚抬不起来，优先考虑：

先排除碰撞过滤、凸包填空隙、关节限位或动作映射错误；只有物理链路正确且 play 也不抬腿时，才做下面的奖励对照实验。

```text
foot_clearance: -0.01 -> -0.02
torques: -0.0002 -> -0.0001
action_rate: -0.01 -> -0.005
smoothness: -0.01 -> -0.005
lin_vel_y 范围缩小
```

如果机器人抖动严重，优先考虑：

```text
smoothness: -0.01 -> -0.02
action_rate: -0.01 -> -0.02
torques: -0.0002 -> -0.0004
learning_rate: 1e-3 -> 5e-4
noise_level: 1.0 -> 0.5
```

如果机器人速度跟踪过快或实际速度偏大：

```text
先区分Isaac Gym也超速，还是仅MuJoCo超速
核对command_scale、观测历史、关节映射、逐物理步PD和关节损耗定义
对比估计速度与仿真真实速度，排查速度估计器的域偏差
只有训练侧确定性play也存在问题时，再讨论奖励和命令范围
缩小 lin_vel_x 范围
加大 torques 惩罚
加大 action_rate / smoothness
```

如果机器人容易摔：

```text
orientation: -0.2 -> -0.3
ang_vel_xy: -0.05 -> -0.1
lin_vel_z: -2.0 -> -3.0
缩小 yaw / lateral command 范围
降低 learning_rate
```

## 训练命令

以下以Primuus为例；Go2改用 `train_go2.py / play_go2.py`，实验目录对应 `logs/go2`。所有训练命令在服务器训练工作区执行。

小步检查：

```bash
cd ~/quadruped_train
python quadruped_rl/scripts/train_primuus.py --headless --max_iterations 100
```

正式训练：

```bash
python quadruped_rl/scripts/train_primuus.py \
  --headless \
  --num_envs 4096 \
  --seed 1 \
  --max_iterations 5000 \
  --run_name rough
```

续训最新 checkpoint：

```bash
python quadruped_rl/scripts/train_primuus.py \
  --headless \
  --resume \
  --max_iterations 5000
```

指定 run 和 checkpoint：

```bash
RUN='<run目录名>'
python quadruped_rl/scripts/train_primuus.py \
  --headless \
  --resume \
  --load_run "$RUN" \
  --checkpoint 1000 \
  --max_iterations 5000
```

导出策略：

```bash
python quadruped_rl/scripts/play_primuus.py --headless
```

默认导出：

```text
logs/primuus/exported/policies/policy_1.pt
logs/primuus/exported/policies/policy_1.onnx
```

默认选择 checkpoint 文件修改时间最新的有效 run，再选其中编号最大的 checkpoint，不按 reward 选优。指定 `--load_run` 时填写完整目录名；`--run_name rough` 不等于可以用 `--load_run rough`。

双模型由同一estimator+actor导出，重复导出覆盖固定文件，不会生成 `policy_2`、不覆盖checkpoint。导出失败后不可混用新旧文件。`play --headless`导出后还会运行仿真，不是仅导出命令。本地Primuus分别使用 `models/primuus/policy.pt`和 `policy.onnx`，复制时须重命名；Go2保留 `policy_1.*`，详见[模型目录](../src/controller/rl/models/README.md)。

## 训练后怎么看是否有效

不要只看总 reward。至少看这些：

```text
rew_tracking_lin_vel     速度跟踪是否提升
rew_tracking_ang_vel     转向跟踪是否提升
rew_foot_clearance       抬脚约束是否稳定
rew_torques              是否为了抬脚导致力矩过大
rew_action_rate          动作是否变抖
rew_smoothness           二阶动作是否变抖
rew_dof_pos_limits       是否频繁接近关节极限
rew_base_height          是否在高度容差内
rew_collision           是否依赖大腿/小腿支撑
rew_foot_slip            是否用滑动代替迈步
rew_turn_step            是否获得有效转向换步
rew_stand_still / rew_stand_contacts  零命令是否保持站姿与足端支撑
episode length           是否频繁摔倒
```

play 观察重点：

```text
脚是否拖地
脚是否抬得过高
机身是否上下跳
转向是否明显晃动
能否连续前进/后退
是否遇到侧向命令就崩
动作是否高频抖动
```

MuJoCo 部署观察重点：

```text
训练 play 和 MuJoCo 是否趋势一致
默认命令下速度是否明显偏大或偏小
键盘按住时命令是否持续、释放后是否清零
摔倒检测是否误触发
关节是否频繁打满
```

## 哪些改动需要同步部署侧

这些训练侧改动必须同步到对应机器人部署配置 `quadruped/src/controller/rl/config/<robot>.yaml`，不修改另一个机器人的配置：

```text
default_joint_angles
control.stiffness / kps
control.damping / kds
action_scale
num_actions
joint_names 顺序
obs_scale_ang_vel
obs_scale_dof_pos
obs_scale_dof_vel
command_scale
history_length
num_one_step_observations
obs 顺序
control_decimation / 控制周期
clip_observations / clip_actions
```

同步的是实际时间而非 decimation 数值：Go2 训练 `0.005*4=0.02 s`，MuJoCo `0.002*10=0.02 s`，策略周期均为50 Hz，但物理步长并不相同。Primuus 是独立机器人配置，训练与play为 `0.002*10=0.02 s`、PD 500 Hz，部署MuJoCo为 `0.0005*40=0.02 s`、PD 2 kHz，两侧策略均为50 Hz，不应覆盖 Go2。离散接触不保证任意高速冲击零穿入。

URDF 描述机械与惯量，XML 描述 MuJoCo 模型和场景，YAML 描述运行配置。机械几何、质量、关节轴向/限位和碰撞载体发生变化时，相关 URDF/XML 及训练资产必须同步；奖励权重不需要搬到部署配置中。Primuus 的具体边界见[模型说明](../src/controller/rl/resources/robots/primuus/README.md)。

Primuus还须同步资源中的 `joint_dynamics.json` 与训练/部署的 `joint_dynamics.py`。定义文件、算法实现和策略训练来源应一同核对；只更新源码或配置不会改变已经导出的权重。

这些通常不需要改部署侧：

```text
reward 权重
noise
friction randomization
base mass randomization
push
terrain curriculum
command curriculum
learning_rate
entropy_coef
num_learning_epochs
num_mini_batches
```

但是如果这些改动导致导出的策略输入格式变化，就必须同步部署侧。
